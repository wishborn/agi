# Wave 4 Memory browser — UI over already-shipped global APIs (v0.4.961, s231)

UX-overhaul Wave 4. Owner: "browse Aion's memories… shared across the whole app.
Aion is one mind."

## The whole wave was UI — verify the backend exists before assuming a backend slice
- The exploration flagged this as potentially needing backend work. It didn't:
  `GET /api/memory/events` + `GET /api/memory/search-docs` already exist
  (server-runtime-state.ts), and api.ts already had `fetchMemoryEvents` +
  `searchMemoryDocs` + `MemoryEvent`/`MemoryDocChunk` types. So Wave 4 = a new
  `routes/memory.tsx` page + route + nav, zero backend. Lesson: grep for the
  endpoint/wrapper BEFORE scoping a backend slice — the data layer for "browse X"
  is often already there from a prior cycle.
- Memory is global per-Aion (keyed by entityId, optional projectPath), NOT
  per-channel — so the page is framed "Aion's Mind, one shared memory" and lives
  at top-level /memory (Knowledge nav), not under a channel.

## Shape
- Two tabs: Memories (semantic `q` + project filter → episodic event cards with
  summary/tags/confidence/createdAt/projectPath) and Knowledge docs
  (searchMemoryDocs over the hardened tier). Empty states for both. PAx
  Card/Badge/Input/Tabs.
- e2e route-mocks /api/memory/events for deterministic row + empty-state asserts
  (same pattern as the identity-people + contribute specs — route-mocking is the
  reliable way to test data-driven pages without a seeded VM).

## Verification
- typecheck/lint/build/orphan/route-check green; e2e +2. Live data is deploy-
  gated (real memory events accumulate on the running gateway).
