# Wave 1 Identity — the bug wasn't what it looked like (v0.4.950-953, s228)

UX-overhaul Wave 1. Owner: "Pending Identity… no way of seeing who's approved or
managing them… doesn't seem to remember who the users are."

## The reported bug was a misdiagnosis trap (read the code first)
- "Doesn't remember who the users are" SOUNDED like a persistence bug. It wasn't:
  `PendingApprovalStore` ALREADY persisted to `~/.agi/pending-approvals.json`
  (slice 7, fully wired + 27 tests; the store is constructed WITH `persistPath`
  in server.ts). The real bug: `approve()`/`reject()` **deleted the pending
  record and kept only `{status, decidedAt}`** — the person (name, channel,
  projects, registration) was discarded. So there was nothing to LIST. Fix =
  retain a person snapshot on the decision, not "add persistence." Reading the
  store + its construction site before coding saved building the wrong thing.
- Slices: 1a store retains person + listDecisions/updateAssignedProjects/
  clearDecision (33 tests); 1b thin endpoints (GET people?status, PATCH projects,
  POST revoke, POST re-review); 1c IdentityPeoplePanel (Card/Badge/Button/Popover,
  +2 route-mocked e2e); 1d Discord-owner.

## The Discord-owner ask: the field already existed
- Owner: "set which Discord user is the Owner, on the Channels page." The field
  `owner.channels.discord` already existed AND was settable in Settings → Owner
  Channel IDs (Settings.tsx). The ask was PLACEMENT (Channels page), not a missing
  feature. Built a small reusable DiscordOwnerCard surfacing the existing field
  via `useConfig().save` — no new endpoint/schema. (Wave 3 Channels redesign can
  relocate it.)

## Reusable mechanics
- `PATCH /api/config` accepts dot-notation `{key:"owner.channels.discord", value}`
  and walks the path, preserving siblings — but reusing `useConfig().save(merged)`
  (full PUT) was simpler here and matches Settings.tsx.
- server-runtime-state.ts is a monolith (no isolated inject harness); thin
  guard→store→reply endpoints are verified by typecheck + route-check + the UI
  e2e, with the LOGIC unit-tested at the store layer.
- PROCESS GOTCHA: `pnpm lint | tail -1` returns tail's exit (0) even when lint
  fails — a real lint error slipped into a commit. Never pipe lint when gating;
  grep "Found N warnings and M errors" and require M=0 (or check the raw exit).
